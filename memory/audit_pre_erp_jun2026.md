Owner refers to items by ID (e.g. "do ERPREADY-01"). **Counts:** P0 2 · P1 20 · P2 62 · P3 37 (total 121; 66 high-stakes verified-real).

## Headline

This is a capable, feature-rich single-operator administrator that works well in practice, but it is NOT structurally ready to become a finance ERP without a deliberate hardening pass. The codebase has two distinct write layers — a transaction-capable Drizzle pool used in only 2 files, and a transaction-incapable supabase-js HTTP client used almost everywhere — so virtually every multi-row mutation (task create/move, asset assign/return, person offboarding, stock movements, request conversion) runs as a sequence of independent HTTP calls with no atomicity and, in several places, swallowed errors that report success on failure. Layered on top are float-typed money columns summed in JS, count-based reference numbering with no uniqueness guard, and a recurring family of unescaped-ILIKE lookups (identity resolution, portal login, AI command company/task matching) plus check-then-act races (leave, stock) that are low-probability today on a single-operator tool but become real once money and concurrency arrive. There is one genuine P0 access-control leak (a manager can exfiltrate any colleague's phone number and open-task list across all 7 companies). Functionally, several features silently misbehave — archived tasks pollute every KPI and the Director Brief, task delete loses conversation history under an "undo" toast, monthly-recurring calendar dates drift, and the home compliance count under-reports. Finally there is substantial accumulated cruft: ~20 fully-dead components/modules, three+ overlapping modal/dialog shells, and roughly a dozen copy-pasted helpers (initials, relative-time, date-format, status-tone), alongside CLAUDE.md/route docs that no longer match the live Worlds navigation. None of this is unrecoverable — the fixes are well-scoped — but the transaction, money-precision, and numbering foundations must be addressed before any ledger is built.

## ERP-readiness verdict

NOT READY to pour a finance ledger on top of as-is — but the gaps are well-defined and fixable before the ERP build, not a rewrite. Three foundations MUST be fixed FIRST, in order: (1) Transaction atomicity. The dominant write client (supabase-js / PostgREST over HTTP, used in ~167 files) has NO transaction primitive; the only atomic path (Drizzle db.transaction) is used in just 2 files. Multi-write orchestrations (task create/move, asset assign, request-convert, person offboarding, leave) run as independent HTTP calls with no rollback (ERPREADY-01, DBSPINE-02, ACTHRMS-01, ACTTASKS-04). A GL cannot post a balanced multi-leg journal, an invoice+lines, or a payment+ledger-movement atomically on this base. Rule to establish now: any mutation touching >1 row/table goes through db.transaction or a single Postgres RPC. (2) Money precision. All existing money columns (stock_items/stock_purchases.unit_cost, assets.purchase_cost) are doublePrecision (IEEE-754 float) and are summed in JS (DBSPINE-01, ERPREADY-02); there is zero numeric/decimal convention anywhere. Migrate money to numeric(14,2)/integer-minor-units and mandate it for every new money column before the GL is designed. (3) Sequence/number allocation. Letter refs (and task/request codes) use COUNT(*)+1 / max-scan with no uniqueness guard, producing duplicate and gapped reference numbers (ACTCOMMS-01, ERPREADY-04, DBSPINE-06, ERPREADY-05). Copied into invoice/PO numbering this yields duplicate invoice numbers — a tax/audit failure. Use a Postgres sequence or per-series counters table updated in-transaction + a UNIQUE constraint. Also fix the one open P0 security leak (ACTPORTAL-01) before anything else. Beyond those, harden the resolver/race patterns (ILIKE identity matching, check-then-act stock/leave guards) and clear the dead-code so the ERP build starts on a clean component/route map.

## Fix-first (in order)

1. **ACTPORTAL-01** — Only confirmed P0: a manager (lowest management role) can pass any active personId via a public server action and receive that person's mobile number plus their open-task list across all 7 companies — a direct cross-person/cross-company exfiltration with no RLS backstop. Add the directReportIds/personCanSeePerson guard before returning waHref.
2. **ERPREADY-01** — Structural blocker to a correct ledger: the dominant supabase-js write client has no transaction, so a balanced multi-leg journal/invoice+lines/payment+movement cannot post atomically. Route all multi-statement money writes through db.transaction or a Postgres RPC and make >1-row mutations transactional by rule, before any GL is built.
3. **DBSPINE-02** — Same root cause across hot paths today (task create leaves orphaned task/missing audit on mid-sequence failure). Establishes the mandatory transactional pattern every ERP write path (invoice, bill, payment, stock movement, payroll) must follow.
4. **ACTCOMMS-01** — Letter reference numbers use COUNT(*)+1 with no uniqueness constraint and collide when a draft is deleted — duplicate refs on legally-significant issued letters. This exact numbering scheme copied into AR invoice/PO numbering yields duplicate invoice numbers (tax/audit failure). Fix with a sequence/counter table + UNIQUE before invoices exist.
5. **ERPREADY-04** — Same count-based, no-uniqueness numbering risk articulated at the ERP-readiness level — must be replaced with atomic per-series sequences and a gapless-numbering policy decided before invoice/bill numbering is implemented.
6. **DBSPINE-01** — Money columns are IEEE-754 floats already summed in JS, and there is no numeric convention anywhere for the ledger to copy. Migrate money to numeric(14,2)/integer-minor-units and mandate it for every new money column, or the GL won't reconcile to the penny.
7. **ACTHRMS-01** — Inventory transfer/write-off are non-atomic read-modify-write (absolute writes), so units can duplicate at both sites on partial failure or vanish under concurrency — the direct precursor to the ERP stock sub-ledger. Wrap in a transaction with relative updates.
8. **ACTTASKS-01** — Archived tasks are never filtered, so they inflate every KPI, the Director Brief, and persisted daily_snapshots — a reporting-integrity bug that would corrupt any future period/ledger roll-up keyed off these counts. Surface and exclude archived by default.
9. **ACTTASKS-02** — Task delete cascades away the entire conversation and meeting provenance while the 'undo' toast promises a restore that only brings back the task+assignees — unrecoverable data loss disguised as reversible, and it weakens the audit story the ERP depends on.
10. **ACTPORTAL-02** — Managers can trigger real reminder emails/WhatsApp (from their own address) to any person across all 7 companies and create misattributed Sent outbox rows — a cross-company authorization bypass. Apply the same team-scope guard as ACTPORTAL-01.
11. **COMPIP-01** — Resetting an admin's portal password via the People drawer silently demotes them from group-wide admin (hr) to single-company staff — a privilege/role-integrity regression triggered by an unrelated action, dangerous once finance modules gate on role. Preserve the existing role on password-only reset.
12. **DBSPINE-04** — getOrCreatePersonSb resolves assignees via unescaped ILIKE, so an AI-extracted/pasted name containing % or _ matches the wrong person — wrong-owner assignment in the load-bearing identity resolver the ERP (AR/AP/payroll) will reuse. Escape LIKE metacharacters or use normalised .eq().
13. **AUTHSEC-02** — Portal sessions aren't bound to the password hash or a generation counter, so a self-service password change does not log out other devices for up to 60 days — the expected 'log everyone else out' control silently does nothing. Mirror the admin session-generation pattern.
14. **APICRON-01** — Email automation retries the whole category on partial failure and sends before writing the cooldown row, so a transient transport error mid-loop re-emails already-notified staff — and this is the exact non-idempotent engine a future payroll/invoice-batch job would hang on. Make per-recipient work idempotent independent of markRanToday.
15. **ACTHRMS-03** — Leave over-booking is validated against the current calendar year regardless of the request's actual start date, so year-boundary requests are wrongly accepted/rejected — a leave-maths correctness bug reused by the portal and a precursor to payroll. Anchor the entitlement window to the request's start date.
16. **LIBDERIVE-01** — The home 'Compliance issues' headline counts only the worst 6 owners, so with dozens of staff it under-reports the real total and disagrees with the Director Brief — a wrong compliance figure heading into a compliance-sensitive ERP build. Compute over the full score set.
17. **ACTPEOPLE-03** — Archiving a manager never clears their direct reports' manager_id, so reports keep pointing at an inactive manager — breaking org roll-ups, manager-scoped access, and any future ERP approval routing keyed off manager_id. Null/repoint reports on archive or exclude inactive managers from scope checks.
18. **ACTDOCS-01** — The duplicate-sweep clusters compilation siblings by shared file_hash and steers the operator to archive all but one, destroying legitimately distinct compliance documents (passport/CV/contract) and silently dropping their checklist links. Exclude shared compilation_id rows from the identical-file signal.
19. **DUP-05** — The closed-date transition is copy-pasted 8 times and the portal copy diverges: a director/HR reopening a Closed task leaves a stale closed_date on an open task, silently poisoning any closed-date-based reporting and a future close-period/ledger. Extract one computeClosedDate helper and route all call sites through it.
20. **ACTMEET-01** — Monthly recurrence uses setMonth with no day clamping, so events on day 29-31 (month-end reviews, rent/lease, payroll dates — exactly ERP cadence) drift to the wrong day in the UI and disagree with the exported .ics. Clamp day-of-month to RFC 5545 semantics.
21. **ACTDOCS-02** — buildCompanyRequirementScores performs auto-link DB writes and audit inserts from render/cron/GET paths and can double-write under concurrent renders — hidden writes in 'read' endpoints make audit trails non-deterministic, a real hazard before adding finance reads. Make it pure-read and move persistence to save-time reconcile.

## Themes

### Transaction atomicity & non-transactional multi-write mutations
The prevailing supabase-js HTTP write client has no transaction primitive, so multi-row orchestrations across tasks, assets, people, stock, requests, letters and leave run as independent calls that can half-apply on any mid-sequence failure with no rollback. This is the single biggest structural blocker to a correct GL/AR/AP/payroll ledger; several of these paths also swallow DB errors and report success on failure.

_IDs:_ ERPREADY-01, DBSPINE-02, ACTHRMS-01, ACTTASKS-04, ACTCOMMS-05, ERPREADY-07, ERPREADY-08, ACTHRMS-05, APIROUTES-03, APICRON-01

### Money precision, sequence numbering & ledger-corrupting data shapes
Existing money columns are IEEE-754 floats summed in JS, and reference/code numbering uses COUNT(*)+1 / max-scan with no uniqueness guard — both are exactly the patterns a finance/invoice ledger must NOT inherit. Letter refs already collide on draft delete; copied into invoice numbering this produces duplicate invoice numbers (tax/audit failure).

_IDs:_ DBSPINE-01, ERPREADY-02, ACTCOMMS-01, ERPREADY-04, DBSPINE-06, ERPREADY-05, ERPREADY-09

### Access-control & authorization scoping gaps
A manager can exfiltrate any person's phone number and open-task list across all 7 companies (P0), and can trigger reminder email/WhatsApp to anyone org-wide. A routine password reset silently demotes an admin to staff; portal sessions can't be invalidated on password change; an admin route is unauthenticated.

_IDs:_ ACTPORTAL-01, ACTPORTAL-02, COMPIP-01, AUTHSEC-02, ACTPORTAL-03

### Unescaped ILIKE lookups & check-then-act races
A recurring pattern of feeding raw user/AI input into ILIKE pattern matches (identity resolution, portal login, AI-command company/task matching) and of validating against a derived total then writing without a lock or constraint (leave over-booking, stock negative-guard, request conversion, attendance upsert). Low-probability today but the wrong template for finance lookups and budget/inventory controls.

_IDs:_ DBSPINE-04, AUTHSEC-01, APIROUTES-02, APIROUTES-04, DBSPINE-03, ACTHRMS-02, ACTCOMMS-05, ACTHRMS-07, ERPREADY-06, ERPREADY-10

### Functional correctness bugs (reporting, scheduling, lifecycle)
Archived tasks are never filtered so they corrupt every KPI/snapshot/Brief; task delete loses conversation+meeting history under an 'undo' toast; monthly-recurring calendar events drift for day 29-31 and disagree with the exported .ics; long-running daily recurrences vanish; the home compliance count under-reports; archiving a manager orphans their reports; email automation can double-send on partial failure; leave validates against the wrong leave-year.

_IDs:_ ACTTASKS-01, ACTTASKS-02, ACTMEET-01, COMPBIG-01, COMPBIG-02, ACTMEET-02, LIBDERIVE-01, ACTPEOPLE-03, APICRON-01, ACTHRMS-03, ACTDOCS-01, ACTPEOPLE-01, DUP-05

### Referential integrity & schema gaps
Core org-graph pointers (manager_id, related_person_id) and several other FKs are bare integers with no constraint, so a mis-set id during ERP import would not be caught by the DB; primary manager chains can form cycles; orphan duplicate-numbered migration files sit outside the journal.

_IDs:_ DBSPINE-05, ACTPEOPLE-01, DBSPINE-07

### Dead code & orphaned modules
Roughly 20 fully-dead components and several dead lib/route clusters (digest, forecast, attention/widget/stat-tile families, governance-quick-edit, plus dead exports inside live files) — leftovers of removed routes and superseded iterations that will be mis-copied or mis-extended during the ERP build.

_IDs:_ COMPAH-01, COMPAH-02, COMPAH-03, COMPAH-04, COMPIP-03, COMPQZ-01, COMPQZ-02, COMPQZ-03, COMPQZ-05, COMPQZ-06, DEADCODE-01, DEADCODE-02, DEADCODE-03, DEADCODE-04, DEADCODE-05, DEADCODE-06, COMPBIG-03, ACTTASKS-03, ACTCOMMS-06, ACTCOMMS-02, COMPQZ-04

### Duplication & divergent copies of shared logic
The same logic is hand-rolled across many files and has drifted: status/priority tone helpers (~7 copies, canonical badge-tones.ts bypassed), initials() (~13), relative-time (~15, some with a real UTC-offset display bug), date formatters (~30+), modal shells (3+), manager allowed-statuses (4 copies that disagree between desktop/mobile), and the closed-date transition (8 copies, the portal one leaves a stale closed_date on reopen).

_IDs:_ DUP-05, DUP-01, PAGESUI-01, DUP-03, COMPIP-08, DUP-02, COMPBIG-05, COMPIP-04, DUP-04, DUP-06, DUP-07, COMPIP-02, COMPBIG-04, COMPIP-05, COMPIP-06, COMPIP-09, ACTMEET-05, LIBDERIVE-05, LIBDERIVE-06, ACTCOMMS-07, ACTCOMMS-04

### Performance & read-path roll-up cost
Hot read paths pull whole tables and aggregate in JS: getAllTasks loads every task_update portfolio-wide on each render, compliance scorers run twice per Worlds render uncached, the Worlds layer calls the entire getBrief just to read one field, and report roll-ups (stock valuation, request trends) scan full tables in JS — all of which the ERP will scale up.

_IDs:_ DBSPINE-08, LIBDERIVE-02, LIBDERIVE-03, ERPREADY-09, APICRON-03

### Hidden side-effects in read paths & error-handling hygiene
A 'read' scorer performs DB writes (auto-link + audit inserts) from render/cron/GET paths and can double-write under concurrency, while the person-side scorer diverges and never auto-links; several actions report ok:true regardless of the DB result; quick-update and peek paths confirm success on failure.

_IDs:_ ACTDOCS-02, ACTDOCS-03, APIROUTES-03, ACTHRMS-05, COMPIP-07, LIBDERIVE-04

### Documentation drift vs live code
CLAUDE.md and routes_and_pages.md describe a superseded HRMS-launcher nav (the pill is now Worlds-based), list removed/redirected pages as live, point at the dead org-chart module instead of org-flow, and omit whole live subsystems (Requests, Calendar, Announcements) and ~13 schema tables — a misleading map for the ERP build.

_IDs:_ DRIFT-01, DRIFT-02, DRIFT-03, DRIFT-04, DRIFT-05, DRIFT-06

### AI prompt-injection & minor AI hygiene
Only one of four prose AI endpoints hardens against injection, so staff-writable task content can steer an executive briefing/forwarded email the owner reads; plus minor partial-index and confidence-scaling issues.

_IDs:_ AILAYER-01, AILAYER-02, AILAYER-03

**ERPREADY-01** (P0, erp-risk, verified) — No DB-transaction path for the dominant (supabase-js) write style — multi-statement mutations cannot be atomic
- File: `src/db/supabase.ts:14; src/db/index.ts:21`
- Evidence: Two write paths coexist. The Drizzle pool (`db`, src/db/index.ts:21) exposes db.transaction and is the ONLY atomic path — but it is used in just two files (src/app/companies/department-actions.ts:62/97 and reference-actions.ts:57/72/107/126, all merge ops correctly wrapped in db.transaction). **ACTCOMMS-01** (P1, data-integrity, verified) — Letter reference numbers are not unique and collide when a draft is deleted

**ACTHRMS-01** (P1, erp-risk, verified) — Site-tool inventory transfer/write-off are non-atomic read-modify-write (inventory can be duplicated or lost)
- File: `src/lib/site-tools.ts:217-248`
- Evidence: transferSiteTool() reads src.quantity (line 219-223), then in separate non-transactional sb calls: increments/creates the destination row (lines 234-241) and decrements the source via `remaining = src.quantity - move` written back as an absolute value (line 242-243). writeOffSiteTool() (lines 251-262) similarly reads quantity then writes `src.quantity - off` as an absolute. **DBSPINE-02** (P1, data-integrity, verified) — No transactional atomicity on multi-write mutations — partial writes leave inconsistent data
- File: `src/lib/mutate.ts:33,src/app/task/actions.ts:329`
- Evidence: All writes go through the Supabase PostgREST HTTP client (src/db/supabase.ts), which cannot span a transaction across calls. mutate() (mutate.ts:33-61) only wraps run() in try/catch + records an undo token — no BEGIN/COMMIT. createTask (task/actions.ts:329-387) performs sequential independent writes inside run(): getOrCreateDeptSb (insert), insertTaskWithUniqueCodeSb (insert into tasks), per-assignee getOrCreatePersonSb (insert people) + task_assignees upsert, then audit_log insert (369). **DBSPINE-04** (P1, data-integrity, verified) — getOrCreatePersonSb does an unescaped ILIKE lookup — pattern metacharacters in a name match the wrong person
- File: `src/lib/db-helpers.ts:24`
- Evidence: getOrCreatePersonSb resolves an existing person with sb.from('people').select('id').ilike('name', name).maybeSingle() (db-helpers.ts:21-25). PostgREST ilike treats the value as a LIKE pattern: % and _ are wildcards. A passed name like 'Jitesh%' or any name containing _ matches a different existing row (e.g. 'Jitesh Patel') and returns that person's id. This function is the assignee/owner resolver for task creation across many write paths (task/people/capture/meeting/portal/requests actions).
- Impact: A task can be silently assigned to the wrong person when the typed/extracted name contains a % or _ (AI-extracted names, pasted text, agent names). Wrong-owner assignment is a cross-person data-association defect and pollutes workload/compliance roll-ups. .ilike also uses maybeSingle(), so two case-variant rows would throw rather than dedupe.
- Fix: Escape LIKE metacharacters before the ilike (replace %,_ ,\ with escaped forms) or, better, do exact case-insensitive matching via a normalized lookup (e.g. .eq on lower(name) with a functional unique index) so the dedup key and the lookup use identical semantics. Align the lookup (ilike) and the upsert onConflict ('name', case-sensitive) so they agree.
